\chapter{Lean Axiom-Audit Manifest}
\label{ch:appx-lean-audit}

\noindent\emph{Snapshot of the live baseline of axiom dependencies
for every Lean theorem in the project's library, by module.
$260$ tracked theorems; $170$ axiom-empty, $90$ \texttt{[propext]}-only.}

This appendix is a snapshot of the Lean axiom-audit baseline.  Every
manuscript theorem whose statement is $\Qp$-data has a corresponding
Lean term, and every such Lean term is constrained by continuous
integration to a permitted axiom set.  The manifest below lists the
counts by Lean module; the live baseline against which the CI
checks runs is regenerated by
\codepath{make lean-audit-update} and verified by
\codepath{make lean-audit-strict}.

\section{The axiom discipline}
\label{sec:audit-discipline}

\marginkey{\texttt{[propext]}-only}%

The project enforces a tight axiom budget for load-bearing
theorems.  In Lean~4, theorems can in principle depend on three
axioms beyond pure type theory: \texttt{propext} (propositional
extensionality), \texttt{Classical.choice} (the axiom of choice),
and \texttt{Quot.sound} (well-foundedness of quotients).  The
project's discipline restricts every load-bearing theorem to at
most \texttt{[propext]}; \texttt{Classical.choice} is prohibited
(its absence is the constructive-content guarantee), and
\texttt{Quot.sound} is permitted only when explicitly justified.

The audit is performed by \codepath{scripts/lean\_axiom\_audit.py},
which runs \codepath{\#print axioms} over every tracked theorem
in the Lean library and compares the result against the baseline.
A theorem acquiring a new axiom dependency triggers a CI failure;
a theorem whose axiom set shrinks (the proof became more
constructive) passes silently.

\section{Drift policy}
\label{sec:audit-drift}

The continuous-integration drift policy:

\begin{itemize}
  \item \textbf{FAIL}: a tracked theorem acquires an axiom
    dependency not in the baseline.  This indicates a proof became
    less constructive and requires manual review.
  \item \textbf{PASS (silent)}: a tracked theorem's axiom set
    shrinks.  Re-baselining via
    \codepath{make lean-audit-update} captures the tighter discipline
    going forward.
  \item \textbf{STRICT mode}
    (\codepath{make lean-audit-strict}): also fail on new theorems
    not in the baseline and on tracked theorems missing from the
    build.  Used in the manuscript-bundle release CI pipeline.
\end{itemize}

The strict mode is the gate on the manuscript-bundle release: a
release pipeline that produces this manuscript also produces the
Lean axiom audit with strict-mode pass.

\section{Reproduction}
\label{sec:audit-reproduce}

From the repository root:
\begin{itemize}
  \item \codepath{make lean-build} compiles the Lean library
    (\codepath{cd lean \&\& lake build}).
  \item \codepath{make lean-audit} re-runs the audit and reports
    drift versus the baseline.
  \item \codepath{make lean-audit-strict} same, plus strict-mode
    checks (new / missing theorems).
  \item \codepath{make lean-audit-update} regenerates the baseline
    manifest from the current build state.
\end{itemize}

The companion script
\codepath{scripts/lean\_axiom\_audit.py} is the implementation;
its output (with the per-theorem axiom set) populates the
live baseline checked in at \codepath{lean/AXIOM\_AUDIT.md}.
